### 1.1 The globals every condition tests

**Every condition in every cast submod that is not `IsPlayer`, `IsSneaking`, or `IsEquippedType`
is a `CompareValues` against an ESP global — never against a graph variable, never against a
casting-source query.** The globals used:

| Global | Form | Fork symbol / write site |
| --- | --- | --- |
| `SpellHotbar_SpellAnimationType` | `SpellHotbar.esp` `0x815` | `game_data.cpp:380`, written by `set_animtype_global` (`game_data.cpp:1873-1878`) |
| `SpellHotbar_CastingSource` | `SpellHotbar.esp` `0x835` | `game_data.cpp:382`, written by `set_weapon_dependent_casting_source` (`game_data.cpp:1879-1919`) |
| `SpellHotbar_isCastingConcSpell` | `SpellHotbar.esp` `0x834` | `game_data.cpp:394`, raised to `1.0` at `casting_controller.cpp:866`, cleared in `reset_animation_vars` (`game_data.cpp:1932-1934`) |
| `SpellHotbar_Casttimer` | `SpellHotbar.esp` `0x838` | `game_data.cpp:393` — **not** referenced by any cast submod condition |

`SpellHotbar_CastingSource` holds the raw `RE::MagicSystem::CastingSource` int:
`0 = kLeftHand`, `1 = kRightHand`, `2 = kOther`, `3 = kInstant` (`game_data.cpp:1884-1916`;
`cast_spell` clamps it back to 0..3 at `casting_controller.cpp:1523`). So a submod condition
`0x835 == 0` means *left*, `== 1` means *right*. Dual is **not** encoded here — a dual cast writes
`kLeftHand` (`game_data.cpp:1905-1908`) and is distinguished purely by animation-type id.

`IsEquippedType` `Type: 8` is OAR's staff value, and the `"Left hand"` boolean picks the physical
hand. That condition is the only *equipment* test in the whole vocabulary; it is entirely
independent of both globals.

### 2.2 Which shape enters which presentation path

Dispatch is `try_start_cast` → one of four start functions (`casting_controller.cpp:1290-1307`):

| Press shape | start fn | anim slot chosen | `CastShape` passed to driver | cite |
| --- | --- | --- | --- | --- |
| fire-and-forget, 1H, not dual | `start_cast` | `primary` (`anim2=false`) | `fire_and_forget` | `casting_controller.cpp:1305`, `1045-1075` |
| fire-and-forget, `IsTwoHanded()` **or** `dual_cast` | `start_ritual_cast` | `variant` iff `casttime <= 1.51f` | `fire_and_forget` | `casting_controller.cpp:1300-1302`, `1132-1164` |
| concentration, 1H | `start_conc_cast` | `variant` iff `m_dual_cast` | `channel` | `casting_controller.cpp:1296`, `1077-1102` |
| concentration, `IsTwoHanded()` | `start_ritual_conc_cast` | `variant` iff `casttime <= 1.51f` | `channel` | `casting_controller.cpp:1292`, `1104-1130` |
| potion | `start_potion_use` | — | **no driver call at all** | `casting_controller.cpp:1319-1320`, `1328-1347` |
| shout / power (`FormType::Shout`, `hand_mode::voice`) | `CastingInstancePower` path | — | **no driver call**; selectedPower swap + injected Shout button, vanilla shout graph | `casting_controller.cpp:1356-1420`, `casting_controller.cpp:20-41` |
| weapon art / Custom Ability | `try_start_art` → `ArtDriver::begin` | — | separate `SH2_ArtStart` state | `casting_controller.cpp:1778`, `art_driver.cpp:46-51` |

`fast_cast_threshold = 1.51f` (`casting_controller.h:12`).

**Consequence worth writing into the matrix.** A dual-cast one-handed spell goes through
`start_ritual_cast`, but `chose_default_anim_for_spell` is called with `two_handed = false`, so
the family is `kAimed`/`kSelf` and the *slot* is picked by cast time. A dual cast with
`casttime <= 1.51s` therefore gets id `10016`/`10017` (`cast_dual` / `cast_dual_self`); a dual
cast **slower** than 1.51s gets id `1`/`2` — i.e. the plain single-hand family, with
`SpellHotbar_CastingSource == 0`, and upstream would present it as `cast_1h_left`. Combo of
`casting_controller.cpp:1140-1146` + `spell_cast_data.cpp:96-108`. A genuinely two-handed
(ritual) spell gets `10000`, or `10016`/`10017` when fast.

Also: `hand == dual_hand` on a spell that cannot dual-cast is silently downgraded to `auto_hand`
(`casting_controller.cpp:1269-1273`), so `hand_mode::dual_hand` reaching the driver always means
a real dual cast.

`hand_mode` values are `auto_hand=0, left_hand=1, right_hand=2, dual_hand=3, voice=4`
(`bar/hotbar.h:33-41`).

### 2.3 Where the globals are written, and when relative to state entry

Every one of the four start functions runs the **same fixed order**, and it is the order OAR's
condition evaluation depends on:

1. `GameData::set_animtype_global(anim)` — writes `0x815`
   (`casting_controller.cpp:1057` / `1087` / `1115` / `1146`).
2. `GameData::set_weapon_dependent_casting_source(hand, dual)` — writes `0x835`, returns the
   resolved `hand_mode` (`casting_controller.cpp:1059` / `1089` / `1117` / `1148`).
3. `CastingInstance*` constructed.
4. `arm_spellfire(used_hand)` (`:1061` / `1092` / `1120` / `1150`).
5. `MscoCastDriver::begin(pc, used_hand, casttime, shape)` (`:1062` / `1093` / `1121` / `1151`),
   which writes `MSCO_attackspeed` and then sends the entry notify
   (`msco_cast_driver.cpp:312-319` → `send_entry`, `:181-196`).

**Both globals are therefore already settled before the graph is asked to enter the state.**
`SpellHotbar_isCastingConcSpell` (`0x834`) is the exception: it is raised to `1.0` only once the
channel's charge finishes and the spell actually starts (`casting_controller.cpp:866`), which is
after the start clip has already been chosen — matching upstream's `== 0` start / `> 0` loop split.

Teardown: `GameData::reset_animation_vars()` zeroes `0x815`, the art selector, `0x835`, `0x838`
and `0x834` (`game_data.cpp:1920-1935`). It is deliberately deferred while a clip is still playing
(`animation_vars_reset_pending` / `poll_pending_animation_var_reset`,
`casting_controller.cpp:299-315`) — an armed cast counts as live for this purpose
(`:310`).

`set_weapon_dependent_casting_source` resolution table (`game_data.cpp:1879-1919`):
`auto_hand` + dual → `dual_hand` + `kLeftHand`; `auto_hand` otherwise →
`get_cast_hand_from_equip()`; `right_hand` → `kRightHand`; `left_hand` **and** `dual_hand` →
`kLeftHand`; `voice` → `kInstant`.

### 2.4 What the fork actually presents today

### 3.5 Node pattern per state (what a parallel set costs)

Each state is exactly **five** files plus shared infrastructure:

1. `hkbClipGenerator` — the clip path, `mode MODE_SINGLE_PLAY`, `triggers` → the shared exit
   trigger array, `variableBindingSet` → the shared `MSCO_attackspeed`→`playbackSpeed` binding
   (`magicbehavior/#shtb$12`, `1hm_behavior/#shtb$10`, one binding, `memberPath playbackSpeed`).
2. `hkbStateMachineStateInfo` — `stateId`, `enterNotifyEvents`, `exitNotifyEvents`, `transitions`,
   `generator` → the modifier generator.
3. `hkbModifierGenerator` — wraps the clip in the modifier.
4. `bAnimationDrivenIsActiveModifier` — the commitment/rooting modifier (ADR-0015).
5. `hkbVariableBindingSet` for that modifier — 4 bindings: `bIsActive0→bAnimationDriven`,
   `bIsActive1→bAllowRotation`, `bIsActive2→HKSMoveON`, `bIsActive3→bHeadTrackSpine`
   (`magicbehavior/#shtb$13.txt`).

Arithmetic check: `magicbehavior` holds 31 `#shtb$N` files = 5 states × 5 + 6 shared
(`$1` cast local transitions, `$3` enter notify, `$4` exit notify, `$5` exit trigger, `$12`
attackspeed binding, `$26` channel transitions). `1hm_behavior` holds 36 = 6 states × 5 + 6 shared
(`$1`, `$3`, `$10`, `$24`, `$26`, `$31`).

**A parallel right + dual set (4 clips each), as a scope figure only — not a recommendation:**
per hosting graph, 8 new states × 5 files = **40 new `#shtb$N` files**, ×2 graphs = **80 files**;
plus 8 new entry-event strings per graph in `#0077`/`#0085` (and `MRh_SpellFire_Event` in
`#0085`); plus 8 new transitions in each host transition array (`#1344`, `#4872`); plus 8 new
transitions in the shared cast local-transition arrays (`#shtb$1` in both graphs — or new
per-family arrays); plus 8 new `stateId`s and 8 new entries in each `states` list (`#1346`,
`#4876`); plus `MSCO_right1..4.hkx` / `MSCO_dual1..4.hkx` as clip paths (they already exist as
files, §5/§6). Renaming existing states (e.g. `SH2_CastRight` → a left-named event) would be a
breaking change to `kCastEvents` (`msco_cast_driver.cpp:40-45`) and to every log/trace in the
evidence tree. **A changed file set under `nemesis\Nemesis_Engine\mod\shtb` requires Nemesis
Update Engine before Launch** (global rule; `run-nemesis.ps1 -Tick shtb -Apply -UpdateEngine`).

### 3.6 The existing precedent for OAR-selecting inside a shtb state

## 4. SPELLFIRE CONTRACT

### 4.1 Arming — left-only by construction

```
casting_controller.cpp:130-149
  constexpr uint8_t fire_left{ 1 };
  constexpr uint8_t fire_right{ 2 };
  std::atomic<uint8_t> spellfire_mask{ 0 };

  void arm_spellfire(hand_mode used_hand) {
      (void)used_hand;                 // :145
      uint8_t mask = fire_left;        // :146
      spellfire_mask.store(mask, ...); // :147
      spellfire_seen.store(false, ...);// :148
  }
```

The two-bit mask machinery is already there; only the *selection* is hard-coded. `notify_spellfire`
(`:151-157`) already accepts either bit and is already called for both events.

Raise sites: `animationeventhook.cpp:77-82` —
`MLh_SpellFire_Event → notify_spellfire(true)`, `MRh_SpellFire_Event → notify_spellfire(false)`.
Both are already wired; only the mask stops a right event from committing.

`clear_spellfire()` (`:162-164`) is called at cast start as well as end, because a vanilla-key
shout raises SpellFire with no instance live (`:159-161`).

### 4.2 Vanilla isolation — left-only, and it lives on the hook's front edge

`animationeventhook.cpp:91-118` (`ProcessEvent_PC`):

- `isolate = holder is player && isolate_left_hand_caster_before_vanilla_spellfire(MscoCastDriver::is_active(), tag == "MLh_SpellFire_Event")` (`:97-100`).
  The predicate is `driver_cast_active && is_left_spellfire` (`combo_cache.h:595-599`).
- When true: `pc->GetMagicCaster(kLeftHand)->InterruptCast(true)`, log, run our observer, and
  **return `kContinue` without chaining `_ProcessEvent_PC`** — i.e. vanilla never sees that one
  event (`:101-110`).
- Every other event chains vanilla first, then our observer (`:113-117`).

The second, coarser isolation is `MscoCastDriver::interrupt_left_caster_if_spell`
(`msco_cast_driver.cpp:621-636`): reads `pc->GetEquippedObject(true)` (left), and if it is a
`Spell` or `Scroll`, interrupts the left caster. Called at `begin()` (`msco_cast_driver.cpp:316`)
and from `deliver_armed_payload` (`casting_controller.cpp:254`). Predicate
`isolate_left_hand_caster_for_driver_cast(bool left_hand_holds_spell)` (`combo_cache.h:585-589`).

**Both isolations are left-only. Neither has a right-hand counterpart.** A right-hand clip raising
`MRh_SpellFire_Event` today would reach vanilla unimpeded and could complete an equipped
right-hand spell alongside SH2's own `CastSpellImmediate`. That is the ticket's second spike
question, and it is `UNPROVEN` — no right-hand clip has ever been played by this fork.

### 4.3 Ticket 43's delivery latch — what a hand variant must fold into

Three exits, one latch, at most one armed instance:

- `armed_cast` is a single `std::unique_ptr<CastingInstance>` (`casting_controller.cpp:235`),
  created only in `retire_cuttable_cast` when
  `retired_cast_stays_armed(cuttable, already_delivered)` (`combo_cache.h:652-655`) holds
  (`casting_controller.cpp:329-346`).
- Polled exits: `classify_armed_delivery(already_delivered, spellfire_seen, clip_active)`
  (`combo_cache.h:662-678`) → `on_spellfire` if the event was seen, `on_clip_end` if the clip is
  gone and no event ever came, else `hold`. Driven at `casting_controller.cpp:1018-1034`.
- Unpolled exit — **the cut**: the next press calls `deliver_armed_payload("the cut")` directly
  before starting anything (`casting_controller.cpp:1214`), and so do
  `yield_shtb_for_non_chain_start` (`:268`), the shout/power path (`:1370`) and the potion path
  (`:1335`).
- The actual one-delivery latch is `CastingInstance::deliver_payload`'s `m_spell_started` early
  return (`casting_controller.cpp:639-641`); `deliver_armed_payload` additionally drops the
  instance so no second path can even reach it (`:248-262`).
- A delivery that does **not** arrive through the hook's isolation path re-runs the left-caster
  isolation itself (`casting_controller.cpp:254`, comment at `:240-243`).
- Game load discards an armed payload rather than delivering it into the save being read
  (`:354-356`).

**What a right/dual variant must fold in:** the mask in §4.1 becomes hand-derived; a dual clip may
legitimately raise both `MLh` and `MRh` and must still deliver once — `notify_spellfire` only sets
a bool, so a two-bit mask already collapses to one commitment, and `deliver_payload`'s
`m_spell_started` is the second guard. The isolation in §4.2 needs a right-hand twin **and** a
decision for the dual case (interrupt both casters? the hook currently swallows the one event it
isolates, so swallowing both `MLh` and `MRh` for a dual clip is a behavioural choice, not a
mechanical one). `UNPROVEN` either way.

## 5. DUAL MECHANICS

- **The decision to dual-cast** (`casting_controller.cpp:1257-1273`): requires
  `!spell->GetNoDualCastModifications()`, `(hand == auto_hand && GameData::should_dual_cast()) ||
  hand == dual_hand`, and `GameData::player_can_dualcast_spell(spell)` — the school's
  dual-casting perk (`game_data.cpp:1844-1872`). Cost is multiplied by `fMagicDualCastingCostMult`.
  If those fail and `hand == dual_hand`, the press is downgraded to `auto_hand` (`:1270-1272`).
  `should_dual_cast()` is the MCM global XOR the held `mod_dual_cast` key (`game_data.cpp:1793-1803`).
- **What the engine is told** (`cast_spell`, `casting_controller.cpp:1515-1541`): **one** caster,
  the one named by `SpellHotbar_CastingSource` — which for a dual cast is `kLeftHand`
  (`game_data.cpp:1905-1908`) — and `playerMagicCaster->SetDualCasting(true)` on it
  (`:1531-1533`). **There is no second caster.** Delivery is a single
  `CastSpellImmediate` (`:1541`).
- **Where the dual flag comes from at delivery time**: `cast_spell(get_spell(), m_used_hand ==
  hand_mode::dual_hand, m_spell_proc)` — fire-and-forget at `casting_controller.cpp:650`,
  concentration at `:860`.
- **Presentation today**: `hand_mode::dual_hand` reaches `MscoCastDriver::begin` and is discarded
  (`msco_cast_driver.cpp:261`); the only thing that differs is the animation-type id, and only
  when the cast is fast (§2.2).
- **Upstream's dual family conditions** (§1.2/§1.3): `cast_dual` = `815 == 10016` + `IsPlayer`,
  `interruptible: true`; `cast_dual_self` = `815 == 10017`; `cast_dual_conc` = `815 == 11003` +
  `834 > 0`; `cast_dual_conc_self` = `815 == 11004` + `834 > 0`; each with a `_start` twin on
  `834 == 0`. **No dual submod tests `SpellHotbar_CastingSource` at all** — dual is a distinct id,
  never a source value. There is no dual ward and no dual ritual-concentration family
  (`cast_anim_ids.h:41-49`).
- MSCO ships `MSCO_dual1..10.hkx` and OAR submods `Dual Cast Base`, `Dual Cast Base - Kynetcist`,
  `Dual Cast Variation 1`, `Dual Cast Self Variation 1/2` (§6.3) — so a first-class dual graph
  path has assets available without authoring.

## 6. STAFF

### 6.1 What the fork detects

The only weapon-type inspection is `GameData::getPlayerEquipmentType()`
(`game_data.cpp:793-852`), which switches on `pc->GetEquippedObject(false)` — the **right** hand —
and maps `RE::WEAPON_TYPE::kStaff` → `EquippedType::STAFF_SHIELD` (`:814-819`; the commented-out
block at `:815-818` shows a previous left-hand/shield refinement that was removed). The full enum
is `FIST, ONEHAND_EMPTY, ONEHAND_SHIELD, ONEHAND_SPELL, DUAL_WIELD, TWOHAND, BOW, SPELL,
CROSSBOW, STAFF_SHIELD` (`game_data/equipped_type.h:5-16`).

**A staff in the LEFT hand is never classified as a staff.** The left hand is only examined when
the right hand holds a one-handed melee weapon (`:828-844`), and a left-hand `Weapon` that is not
melee falls to `ONEHAND_SPELL` (`:835-839`). With an empty right hand and a staff in the left, the
function returns `FIST` at `:799-802`. So there is **no left-staff signal anywhere in the DLL**.

Downstream, `get_cast_hand_from_equip()` (`game_data.cpp:1817-1839`) maps `STAFF_SHIELD` (with
`BOW` and `ONEHAND_SHIELD`) to `kRightHand` and everything else to `kLeftHand` — i.e. a
right-hand staff is the one equipment context that flips Auto to the right hand.

`EquippedType` is otherwise used only for hotbar-bar selection (`bar/hotbars.cpp:166-186`,
`bar/hotbar.cpp:577`, `bar/oblivion_bar.cpp:154`) and Ability art classes
(`game_data/art_definition.h:101-169`). It never reaches `MscoCastDriver` or the SpellFire mask.

`art_pack_gen` does parse `IsEquippedType` values out of author condition trees
(`game_data/art_pack_gen.cpp:80-90`, `art_pack_gen.h:67`, `:104`) — but that is the Ability art
pack path, and the header explicitly notes OAR's `IsEquippedType` values are *not* the vanilla
equipped-type enum.

### 6.2 How upstream detects the physical staff hand

Purely `IsEquippedType` with `Type: 8` and an explicit `"Left hand"` boolean — never a global,
never a fork-side classification (§1.2, §1.3):

- `cast_1h_left_staff` — `Left hand: true`; `cast_1h_right_staff` — `Left hand: false`.
- `cast_1h_left_conc_staff` / `_staff_start` — `Left hand: true`;
  `cast_1h_right_conc_staff` / `_staff_start` — `Left hand: false`.
- The `_conc_idle` pair uses the **negated** form (`negated: true`) to hold the non-staff idle set.

The staff condition is **additive** to the hand condition, not a replacement: e.g.
`cast_1h_left_staff` is `815 == 1` **and** `835 == 0` **and** `IsEquippedType 8 Left hand=true`.
So upstream's staff variant requires the *casting source* and the *physical staff* to be the same
hand — the cross-hand case named in the handoff (spell assigned left, staff held right) matches
**no** staff submod upstream and falls through to plain `cast_1h_left`. That is the gap the ticket
asks to decide on, and it is a property of upstream's data, not of the fork.

## 8. Ten most decision-relevant findings

1. Hand, dual and staff reach the graph **only** through two ESP globals; `MscoCastDriver::begin`
   discards the resolved hand (`msco_cast_driver.cpp:261`) and the entry event is chosen purely by
   combo index (`:40-45`, `:54-60`).
2. Both globals are written **before** the entry notify in all four start paths
   (`casting_controller.cpp:1057-1062` and the three parallels), so OAR-at-entry has the values;
   whether OAR *sees* them from inside a live shtb state in both graphs is the open spike.
3. Upstream's whole vocabulary is `CompareValues` on `0x815` / `0x835` / `0x834` plus
   `IsEquippedType 8` with an explicit hand — no graph variables, no caster queries. 30 cast
   submods, tabulated in §1.
4. Left/right is a *casting-source* split within one id; **dual is a separate id** (10016/10017/
   11003/11004) with no source condition at all; staff is an *additive* `IsEquippedType` on the
   single-hand rows only.
5. `MRh_SpellFire_Event` is already registered in `magicbehavior`'s base event table but is
   **absent from `1hm_behavior`** — the shtb patch had to inject `MLh` there
   (`1hm_behavior/#0085.txt:464-474`). A right-hand annotation silently fails in the drawn-weapon
   host until `MRh` is added.
6. `arm_spellfire` already has a two-bit mask and both raise sites are already wired
   (`animationeventhook.cpp:77-82`); only `(void)used_hand; mask = fire_left;`
   (`casting_controller.cpp:145-146`) makes it left-only. Ticket 43's latch is `m_spell_started`
   plus a single `armed_cast`, so a dual clip raising both events still delivers once.
7. **Both vanilla-isolation seams are left-only** and neither has a right twin
   (`animationeventhook.cpp:97-110`, `msco_cast_driver.cpp:621-636`). This is the machinery cost
   the handoff says decides A vs B, and it is entirely unwritten.
8. A dual cast is **one** caster with `SetDualCasting(true)` (`casting_controller.cpp:1523-1533`),
   never two — so "deliver once" is already structural, not a new constraint.
9. **The fork cannot see a left-hand staff at all**: `getPlayerEquipmentType` inspects only the
   right hand for `kStaff` (`game_data.cpp:814-819`), and a right-hand staff is the sole
   equipment context that flips Auto to the right hand (`:1830-1835`). Any staff axis has to be
   built, either in the DLL or left entirely to OAR's `IsEquippedType`.
10. MSCO already ships `MSCO_right1..10`, `MSCO_dual1..10`, `MSCO_lr1..10` plus
    `Base - Left Staff` (6800) and `Base - Right Staff` (6801) keyed on `IsEquippedType 8` — so
    shape B has assets waiting, **and** (`INFERENCE`, `UNPROVEN`) the fork's current left-only
    clips are probably already being staff-swapped by MSCO behind its back.
